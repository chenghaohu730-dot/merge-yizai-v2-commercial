# 《合成亿仔》第二版商业化优化审计报告

审计日期：2026-07-22  
审计对象：本地仓库中的 V1 网页运行版、V1 微信小游戏运行版、现有 Cocos Creator V2 骨架、正式美术与音频资源  
报告用途：作为第二版立项、排期、开发和验收的主依据  

## 一、先说结论

第一版已经不是“粗糙 Demo”：核心物理合成闭环可玩，11 级头像链辨识度较高，糖果合成机视觉方向成立，亿仔正式形象符合白熊、橙黄色口鼻区、黑色大鼻子、粗眉、头饰和清晰 `MAEE` 的品牌规范；开始、暂停、结算、设置、本地排行、成就、分享、存档和基础音频也都已存在。

但它目前更接近“完成度较高的单局小游戏”，还不是“可持续运营的商业化产品”。第二版最重要的工作不是简单再加四个入口，而是建立以下四个闭环：

1. **核心局内闭环**：一局时长、失败压力、合成爽感和难度曲线可量化、可调优。
2. **局外留存闭环**：任务和成就产出亿仔币，亿仔币解锁皮肤，皮肤和排行推动次日回访。
3. **微信社交闭环**：好友榜、周榜、动态成绩分享卡，而不是只保存本地成绩。
4. **商业运营闭环**：埋点、远程配置、版本管理、包体策略、授权合规和可选激励广告。

建议第二版的产品定位是：

> 合成负责“当下好玩”，皮肤、任务和排行负责“明天还来”，分享和可选激励广告负责“传播与变现”。

不建议马上加入复杂剧情、抽卡、重商城、联网账号和多地图。它们会稀释当前最有价值的“轻、快、抽象、易传播”特征，也与本项目既定边界冲突。

## 四、关键流程审计

### 1. 启动页 — 良好

![启动页](./01-启动页.png)

优点：主角、糖果机、主按钮形成单一视觉焦点，品牌辨识和进入意图都很清楚；亿仔形象与 `MAEE` 规范正确。

问题：底部“设置/排行/成就”与主视觉的立体精度不同；页面看不到版本信息、隐私/授权入口或首次玩法提示。第二版应保留当前主构图，只重做底部导航组件、首玩引导和安全区适配，不需要推翻整张启动页。

### 2. 核心玩法初始态 — 良好但缺首次引导

![核心玩法初始态](./02-核心玩法初始态.png)

优点：分数、最高分、下一球、警戒线和三个底部控制的层级清楚，玩法区最大化，操作入口尺寸合格。

问题：首次玩家没有“左右移动—松手掉落—相同合成”的 10–15 秒教学，也看不到本局目标或当前合成链进度。建议只在第一局显示手势、落点虚线与首个必成合成，不长期遮挡玩法区。

### 3. 连续合成 — 核心乐趣成立

![连续合成中](./03-连续合成中.png)

优点：不同等级的尺寸差、颜色差和表情差能快速识别，碰撞后升级反馈明确，适合继续作为第二版核心。

问题：当前主要依赖单一粒子、提示文字和同一合成音效，连续合成没有逐级增强的“连击音阶、镜头、粒子和分数跳字”。第二版应增强反馈，但不要先改掉稳定物理参数；先埋点记录局长、失败层级和掉落次数，再做数值调优。

### 4. 暂停页 — 明确缺陷，P0

![暂停页](./04-暂停页.png)

390×844 视口下，底部三个入口显示为“设… / 排… / 成…”。根因是三个等宽列同时保留左侧 34 px 图标和 48 px 左内边距，又启用了省略号。自动视口测试没有检查可见文案，所以仍判定通过。

第二版应把暂停页改成一个主操作“继续游戏”和三个完整次操作；可以用“仅图标+完整无障碍标签”，或三项纵向/两行布局，不能继续依赖压缩后的省略号。

### 5. 设置面板 — 视觉可用，能力不足且双端不一致

![设置面板](./05-设置面板.png)

网页端只有“声音、震屏”，微信端却是“声音、掉落指引、轻震反馈”。同一个产品已经出现配置和文案漂移。网页“声音”的说明只写音效，实际却同时控制 BGM。

第二版设置至少拆分为：BGM、音效、震动/触感、掉落辅助线；如果加入强反馈，还要提供“减少动态效果”。不必在手机上放精细音量滑杆，两个独立开关通常更清楚。

### 6. 本地排行榜 — 明确商业短板，P0/P1

![本地排行榜空态](./06-本地排行榜空态.png)

当前页面显示最高分 5731，但本地排行仍为空，说明“最高分”和“历史局记录”是两个独立数据模型，没有做旧数据迁移或统一。即使修好，本地榜也无法形成微信社交竞争。

第二版应保留本地榜作为离线降级，再增加好友榜和周榜。好友榜使用微信开放数据域；周榜/赛季榜使用云端服务并做服务端校验，不能直接信任客户端上传分数。

### 7. 成就 — 有进度，没有奖励闭环

![成就系统](./07-成就系统.png)

当前成就能显示进度，但没有奖励、领取、皮肤关联或回访理由；网页端还出现“完成 1 局网页试玩”等生产环境不应出现的文案。微信端与网页端的成就名称和条件也不是同一套。

第二版应让成就产出亿仔币、皮肤碎片或称号，并区分一次性成就与每日任务。奖励领取要有明确反馈，但不建议引入随机抽卡。

### 8. 重开确认 — 防误触有效，信息表达不足

![重开确认](./08-重开确认.png)

有二次确认是正确的，但弹层只有两个按钮，没有标题和“本局进度将丢失”的后果说明，且按钮是 CSS 渐变风格，与图像化糖果 UI 不完全一致。

第二版应使用统一弹窗组件：标题、后果说明、取消、危险操作；危险按钮要保持红色，但与其他按钮共用同一材质、阴影和按压态。

### 9. 长局与失败节奏 — 高风险，需要数据验证

![长局仍未结束](./09-长局仍未结束.png)

在受控的连续掉落检查中，超过 220 次掉落操作、分数达到 2200 后仍未自然结束。该操作节奏不等同真实玩家，所以不能直接断言“失败逻辑坏了”；但它足以说明当前自然失败、局长和警戒线压力没有被现有自动测试覆盖。

第二版上线前必须记录每局时长、掉落次数、首次警戒、警戒累计、最高等级和失败原因，并设一个初始设计目标再用数据校准。可先以“多数普通玩家单局 4–7 分钟、极长局不超过约 12 分钟”为待验证目标，而不是直接写死数值。

### 10. 结算页 — 信息完整，但仍是试玩口径

![当前构建结算页](../../../tests/device-checks/acceptance-v3-local-assets/result-modal.png)

本图由本次重新运行的当前验收脚本生成。分数、最高合成、今日目标、成就、重开和分享入口齐全；但“新成就：初次试玩”仍泄漏测试口径，主按钮、次按钮和底部三个入口的视觉材质也不完全统一。

第二版结算页应成为核心转化页：本局分数、好友/周榜名次变化、任务进度、获得亿仔币、皮肤解锁进度、再来一局和动态分享卡。信息要分批出现，不能一次塞满。

## 六、用户提出的四个方向，应该怎样做

### 1. 皮肤系统

#### 现状判断

现有 Cocos 目录中已经有 `jelly / star / cream / coin / festival` 五组皮肤，每组 10 级和一张预览图；但商店配置却使用 `classic_round / candy_gloss / sticker_edge`，完全对不上。`FaceSpriteRegistry` 只按等级加载默认头像，也没有读取 `selectedSkinId`。因此当前皮肤资源只能当视觉探索，不能当作已接入。

现有五组图也有一个产品问题：它们把原有“抽象头像链”替换成了果冻、星星、甜品、金币和节日图标，皮肤差异大，但原角色身份几乎消失。节日组可做限时活动，经典长期皮肤应保留原 10 个头像的五官和性格，只改变材质、边框、配色或局部装饰。

#### 第二版建议

皮肤数据统一成单一清单：

```text
skin_id
name
theme
face_01 ... face_10
preview
unlock_type
price
version
bundle_name
availability
```

规则必须锁死：

- 皮肤只改视觉，不改半径、质量、掉落概率、分数和碰撞参数。
- 第 11 级亿仔默认保持正式形象；如以后做亿仔皮肤，仍必须保留白熊、橙黄色口鼻、黑色大鼻子、粗眉、头饰和正面清晰 `MAEE`。
- `MAEE` 不可省略、替换、拼错、镜像、倒置或遮挡。
- 皮肤资源走分包；55 张现有图片已约 4.13 MiB，绝不能进当前主包。
- 首发只选 2 套真正完成的长期皮肤，加经典默认套；节日组后置，避免一次上线五套但质量不一致。

推荐局外闭环：

```text
每日任务/成就/周榜 → 亿仔币 → 解锁皮肤 → 装备展示 → 分享/排行展示 → 回访
```

不建议抽卡。可以使用明确价格、成就解锁和活动兑换，降低开发复杂度和合规风险。

### 2. 音效与 BGM

#### 现状判断

当前 7 个音频总计约 1.05 MiB，其中 6 个 WAV 占 668 KB；BGM 是 32 秒、96 kbps 的 MP3。普通合成和亿仔音效在运行资源中都被裁剪到 2 秒。代码只提供一个总开关，BGM 音量固定 0.24，其余大多固定 0.55；连续合成会反复从头播放同一音效，没有音高/音色变化和混音总线。

#### 第二版建议

建立四条音频总线：

- BGM：主页、局内、警戒/结算可共用主题变体。
- Gameplay SFX：掉落、碰撞、普通合成、高级合成、亿仔、警戒、失败。
- UI SFX：按钮、弹窗、购买、装备、领取、排行结算。
- Haptic：普通合成轻震、高级合成与亿仔分级反馈。

重点不是增加数量，而是做“合成音阶”：连续合成时音高、粒子和分数反馈逐级上升，高等级合成压低 BGM 约 200–400 ms，亿仔出现有独立品牌短旋律。还要处理切后台、来电/音频焦点、暂停、静音和恢复。

设置页改为 BGM、音效、震动、掉落指引四项。音频优先使用自制、定制或买断素材；若继续使用 CC BY 4.0，必须在游戏内或可达的许可页完成署名。

### 3. 排行榜系统

建议拆成三层：

1. **本地榜**：离线降级和历史局记录，修复与最高分不同步的问题。
2. **好友榜**：微信开放数据域渲染好友头像、昵称和最高分。
3. **周榜/赛季榜**：云端存储，支持周重置、赛季结算和皮肤/称号奖励。

排行榜不能直接相信客户端分数。服务端至少校验：版本号、局长、掉落次数、最高等级、分数增长范围、提交频率和异常设备；高分段保留人工/规则复核。不要把 AppSecret 放进客户端。

榜单界面必须有加载、空态、离线、授权失败、服务失败和重试状态。好友榜优先于全服榜，因为它更符合微信传播；周榜奖励只给外观和称号，不给改变物理数值的能力。

微信小游戏官方维护的 API 类型定义仍覆盖小游戏平台能力，并说明类型文件由平台文档自动生成，可作为接入时的接口基线。参见[微信小游戏 API 类型定义](https://github.com/wechat-miniprogram/minigame-api-typings)。

### 4. UI 统一重制

用户提出“把现有代码绘制的 UI 全部重新生成”，方向正确，但执行时要分层。当前开始背景、机台、按钮、设置/排行/成就框、行背景、开关和图标已经是图片资源；真正必须保留代码绘制/动态布局的内容包括：

- 分数、最高分、下一球、倒计时、排行数据、任务进度和本地化文字。
- 真实点击区域、滚动区域、加载/错误状态和安全区。
- 物理球位置、警戒状态、粒子、连击数字和动态效果。

不能把整屏文字和动态数据烘焙进 AI 生成图片。正确做法是建立一套可复用 UI 组件库：

| 组件 | 必备状态 |
| --- | --- |
| 主按钮 | normal / pressed / disabled / loading |
| 次按钮 | normal / pressed / disabled |
| 图标按钮 | normal / pressed / selected / disabled |
| 弹窗 | 标题、正文、单按钮、双按钮、危险操作 |
| 标签页 | normal / selected / badge |
| 商店卡 | locked / affordable / owned / equipped |
| 排行行 | self / top3 / normal / loading |
| 任务行 | in-progress / claimable / claimed |
| 系统状态 | empty / loading / offline / error / retry |

视觉资源采用透明 PNG/WebP、图集和九宫格拉伸；文字、数字和列表保持动态。统一色板、字体、字号、描边、圆角、阴影、内边距和动效时长。所有页面至少验收 320×568、360×740、390×844、430×932，并处理微信安全区和胶囊按钮。

## 七、用户没有提到，但商业化质量必须补的部分

### 1. 首局教学与新手成功体验

- 首次进入只教一个动作，不弹长说明。
- 前 3 次掉落可以用受控序列保证至少一次合成。
- 第一次高级合成时解释警戒线和失败条件。
- 教学完成后不再强制，可在设置里重看。

### 2. 每日任务、成就与连续天数

当前连续天数有逻辑缺陷：跨日时只重置当天目标，保留旧 `streak`；无论中间漏了几天，下一次达标仍会直接 `+1`。第二版需要保存 `lastClearDate`，按真实相邻自然日计算连续天数。

建议首发每日任务只保留 3 个：完成 1 局、合到指定等级、完成若干次合成。分享任务不应每天强迫玩家分享。一次性成就负责长期目标，每日任务负责币产出。

### 3. 动态分享

当前微信分享使用固定 `share_card.png`，只有标题随分数变化。第二版应生成动态分享卡，至少包含：分数、最高合成、好友名次变化、已装备皮肤和亿仔形象；所有出现亿仔的卡片继续严格执行 `MAEE` 规范。

### 4. 数据与远程配置

第二版第一批埋点建议：

```text
app_start / home_view / start_click / tutorial_step
drop / merge(level) / combo / warning_enter / warning_exit
game_over(duration, drops, score, max_level, reason)
task_view / task_claim
skin_preview / skin_unlock / skin_equip
rank_view / score_submit / rank_settle
share_click / share_success
ad_request / ad_show / ad_complete / reward_granted
error / asset_load_fail / cloud_fail
```

核心指标：首局开始率、教学完成率、首局结束率、中位局长、掉落次数分布、失败等级分布、D1/D7、每日任务领取率、皮肤解锁/装备率、排行参与率、分享率和广告完整观看率。

当前没有线上基线，不建议在报告里虚构 D1/D7 目标。先用第二版灰度数据建立基线，再制定提升目标。

### 5. 可选变现

第二版可以加入用户主动触发的激励视频，但只放在两个位置：

- 每局最多一次“继续/缓解警戒”机会。
- 领取额外亿仔币或活动币。

不建议首版就加强制插屏或频繁 Banner，它们会破坏当前单局节奏。激励必须等完整观看后再发放，并处理无广告、加载失败、中途关闭和重复回调。平台文档说明激励视频需先获取广告能力/广告位，并根据完整观看状态发奖，参见[腾讯云小游戏激励视频广告文档](https://intl.cloud.tencent.com/zh/document/product/1219/68612)。

### 6. 可访问性与舒适度

当前移动端三个主控制约 50–54 px，点击尺寸基本合格；但 Canvas 内分数和玩法状态没有完整语义，部分浅色文字对比度未做量化验证，警戒线对色觉差异用户不够友好。

第二版至少做到：警戒同时使用颜色、倒计时和震动；支持关闭震动/减少动态；所有弹窗焦点和关闭逻辑一致；文字不依赖图片；低端机仍能稳定读清分数与提示。最终需要真机和实际对比度测量，本次截图不能证明完整无障碍合规。

## 八、工程与发布路线

### 1. 只保留一个正式核心实现

当前 Web 和微信分别维护一套大文件，已经出现设置、成就、文案和存档结构不一致。Cocos V2 又是第三套。第二版不能同时扩展三套运行逻辑。

建议把现有物理参数和玩法行为冻结成“黄金参考”，补充可重复的合成/失败测试，然后完成 Cocos Creator 3.8 的正式迁移：核心逻辑、UI、存档、任务、皮肤统一在 Cocos；微信、Web 只做平台适配和预览出口。

现有 Cocos 骨架可以复用，但不得把“结构验证通过”当作迁移完成。开工门槛是：安装并锁定 Cocos 版本、创建真实场景/Prefab、接入默认头像链、在编辑器运行、导出微信、真机对比 V1 手感。

如果最终不迁 Cocos，也必须把当前 TS 核心抽成共享模块，由 Web 和微信适配层共同调用；不能继续手工同步两个单文件版本。

### 2. 包体与资源

建议内部主包预算设为不超过 3.3 MiB，给微信基础库差异、版本元数据和紧急修复留余量。首屏、默认头像链、核心 UI、基础音频进主包；皮肤、活动、额外 BGM、动态分享资源进入分包或远程资源。资源清单要带 hash、版本、尺寸、透明边界和授权信息。

### 3. 测试补强

现有测试要新增：

- 自然失败测试，不允许只调用测试钩子强制结算。
- 100–1000 局模拟，输出局长、掉落数、最高等级和异常长局分位数。
- 暂停/结算/设置/排行/商店的文字溢出截图断言。
- Web 与微信配置、任务、成就和存档 schema 一致性检查。
- V1 → V2 存档迁移，包括最高分与空排行修复。
- 皮肤只换视觉、不改变物理参数的自动断言。
- 网络失败、云榜超时、广告失败和离线降级。
- 音频切后台、静音、恢复和连续播放。
- 主包/分包大小预算门禁。

## 九、第二版执行顺序

### 阶段 0：修地基

- 修复暂停菜单、重开说明、试玩/原型文案和本地最高分—排行迁移。
- 修复连续天数算法。
- 修复/建立 Git 仓库与版本发布标签。
- 完成音频许可处理。
- 加入核心埋点、错误日志、性能采样和自然失败测试。
- 确定唯一正式技术路线，完成主包/分包方案。

退出条件：线上/本地版本可追溯，关键 UI 无截断，能看到真实局长分布，主包有明确余量。

### 阶段 1：统一产品与美术底座

- 锁定 UI token、组件清单、按钮/弹窗/列表状态。
- 完成 Cocos 正式场景和 Prefab，或完成共享 TS 核心模块化。
- 重制开始、暂停、设置、任务、商店、排行、结算所需组件资源。
- 默认头像链和亿仔形象做品牌复核。

退出条件：同一套组件覆盖全部页面，动态文字不烘焙，四类手机尺寸无截断，V1 核心手感对比通过。

### 阶段 2：留存闭环

- 每日任务、一次性成就、亿仔币。
- 皮肤预览、解锁、购买、装备和存档迁移。
- 首发 2 套长期皮肤，皮肤资源分包。
- 品牌 BGM、合成音阶、UI 音效和独立设置。

退出条件：玩家可从一局获得币、解锁并装备皮肤，所有皮肤不改变物理数值，音频在真机无爆音/抢占错误。

### 阶段 3：微信社交闭环

- 本地榜修复、好友榜、周榜和赛季结算。
- 云端分数校验、异常检测和离线降级。
- 动态分享卡与分享回流参数。

退出条件：好友榜和周榜在真实微信账号/真机可用，作弊分数不能直接入榜，分享卡正确展示皮肤与 `MAEE` 亿仔。

### 阶段 4：商业化与上线验收

- 视后台资质接入用户主动激励视频。
- 灰度远程配置、皮肤轮换和轻量活动。
- 低端 Android、iPhone、长短屏、弱网、切后台和长局测试。
- 版本说明、隐私、授权、音频许可、备案变化和素材包同步。

退出条件：变现不打断核心局、数据可对账、发布包可复现、线上监控和回滚方案可用。

## 十、第二版验收标准

### 核心玩法

- 自然失败与结算可重复触发，无无限长局。
- 记录局长、掉落数和失败等级分布；根据真实数据确认目标区间。
- 合成、警戒、失败、暂停和恢复无状态错乱。
- 低端目标机尽量保持 60 FPS，长局无持续内存增长或明显卡顿。

### 皮肤

- 经典 + 至少 2 套完整可装备皮肤。
- 解锁、购买、装备、重启、跨版本迁移全部正确。
- 皮肤不改变任何玩法数值。
- 皮肤走分包；加载失败自动回退经典皮肤。
- 亿仔形象 100% 通过品牌强制规范。

### 音频

- BGM、SFX、震动独立控制。
- 连续合成有可辨识层级，高级合成与亿仔有独立标识。
- 切后台、来电、暂停和恢复正确；无明显削波、爆音和循环接缝。
- 所有音频来源、授权和修改记录可追溯。

### 排行与社交

- 本地榜、好友榜、周榜都具备完整 loading/empty/offline/error 状态。
- 客户端伪造分数不能直接上榜。
- 赛季结算与奖励不影响物理公平性。
- 动态分享卡显示分数、皮肤、名次和合规亿仔形象。

### UI 与适配

- 320×568、360×740、390×844、430×932 无截断、遮挡和误触。
- 所有按钮有 normal/pressed/disabled，必要时有 selected/loading/locked。
- 动态文字和数据不烘焙进整屏图片。
- 微信安全区、胶囊按钮和长短屏通过真机验收。

### 工程与发布

- 正常 Git 仓库、版本标签、变更记录和可复现构建。
- 单一核心代码源，平台差异只在适配层。
- 主包内部预算不超过 3.3 MiB，皮肤/活动资源分包。
- 构建、自然失败、视口、存档迁移、排行榜降级和包体门禁全部自动化。
- 正式 AppID、隐私配置、授权清单、音频许可和线上回滚方案齐全。

## 十一、最终优先级建议

如果只能先做一轮，不要按“皮肤 → 音效 → 排行 → UI”顺序各做一点。建议按下列顺序完整交付：

1. **P0 地基**：埋点、自然失败节奏、可见 UI 缺陷、存档迁移、Git、许可、包体。
2. **统一 UI 与单一代码源**：否则后面的每个功能都会返工两次。
3. **任务—亿仔币—皮肤闭环**：这是第二版最直接的留存提升点。
4. **品牌音频与局内反馈**：直接提升成片感和核心爽感。
5. **好友榜/周榜/动态分享**：形成微信社交传播。
6. **有数据后再加激励广告和节日活动**。

一句话概括：第二版不应只是“第一版加几个页面”，而应把现有好玩的合成核心，升级成一个有留存、有社交、有数据、可持续迭代、能稳定发布的微信小游戏产品。
